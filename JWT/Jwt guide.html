Security reference

Public & Private Keys

From asymmetric cryptography fundamentals to JWT attacks and common implementation mistakes.

Section 01

Fundamentals

Asymmetric cryptography uses a mathematically linked key pair. The two keys are generated together using algorithms like RSA or Elliptic Curve Cryptography — but you cannot reverse-derive one from the other.

PUB

Public key

Shared freely with anyone. Used to encrypt data for the owner, or to verify a signature the owner created.

PRIV

Private key

Kept secret by the owner. Used to decrypt data encrypted with the public key, or to sign data.

ALG

One-way relationship

Deriving a private key from its public key is computationally infeasible — the core security assumption of the entire system.

The two operations

GoalOperationSender usesReceiver uses
Keep data secret Encryption Recipient's public key Own private key
Prove identity Signature Own private key Sender's public key
→ Memory hook: Sign with your private key so others can verify with your public key. Encrypt with the recipient's public key so only they can decrypt with their private key.

Where public keys are used

TLS

HTTPS / Web security

Server presents a certificate with its public key. Browser verifies it against a Certificate Authority. Secure session established.

SSH

Remote access

You store your public key on the server. Authentication uses your private key locally. No password required.

SIG

Code signing

OS verifies software updates using the developer's public key. Used by Windows Update, Apple iOS and macOS.

Section 02

How authentication works

Authentication via digital signatures is a two-phase process. The sender signs; the receiver independently verifies. Neither party needs to share a secret.

Phase 1 — Signing (sender)
1
Take message M
2
Compute hash: H = hash(M)
3
Sign hash with private key: S = Sign(H, priv)
4
Transmit (M, S) to receiver
Phase 2 — Verification (receiver)
1
Receive (M, S)
2
Hash the message: H1 = hash(M)
3
Recover from signature: H2 = Verify(S, pub)
4
If H1 == H2 → authentic and unmodified
→ The receiver independently hashes the message and compares it to what was recovered from the signature. A match means the message came from the real sender and was not tampered with in transit.
! Key insight: No shared secret is ever transmitted. The public key used for verification can be known by everyone — that's the point.
Section 03

JSON Web Tokens

A JWT is a self-contained, tamper-evident token. Three base64url-encoded parts separated by dots.

header
.
payload
.
signature
{ }

Header

Declares the signing algorithm — e.g. HS256, RS256. Attacker-controlled input. Never trust it blindly.

{ }

Payload

Contains claims: user ID, role, expiry, etc. Not encrypted — only base64 encoded. Anyone can decode it instantly.

sig

Signature

Proves that header + payload were not modified since signing. Does not prove the claims inside are correct or authorised.

! Critical: JWTs are not encrypted by default. The payload is trivially decodable by anyone. Never store passwords, API keys, or sensitive PII in a JWT payload.

Symmetric vs asymmetric signing

Case 1 — Symmetric (HS256)

Both parties use the same secret to sign and verify. The secret must be shared between all verifiers.

signature = HMAC(secret, header + payload)

Simpler setup, but the secret must stay secret on every verifying server.

Case 2 — Asymmetric (RS256)

Server signs with private key. Anyone verifies with the public key. Public key can be freely distributed.

sign   → private key (server only)
verify → public key (anyone)

Preferred for distributed systems. No secret needs to be shared with verifiers.
